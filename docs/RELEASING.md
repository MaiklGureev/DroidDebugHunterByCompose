# Release process

**English** | [Русский](RELEASING.ru.md)

The `Release` workflow builds Windows x64, Linux x64 and macOS arm64/x64, verifies private Java, and produces installers/portable archives. Users do not need a system JDK/JRE. Public images exclude external Android/Python tool bundles.

Test packaging helpers with `python -m unittest discover -s scripts -p 'test_*.py'`. Gradle's project version, `packageVersion`, release notes and workflow `RELEASE_TAG` must match.

Release workflow/script/help changes and source changes in `master` trigger four builds. Publication runs only for an explicit `release:` commit-message prefix or a manual `workflow_dispatch`. The current configured release is `v1.1.3`; update the version and notes deliberately for a new release.

After all targets succeed, publication checks each file's source commit, version, size and SHA-256. It creates `SHA256SUMS.txt`, a draft release and a tag at the exact build commit, uploads all installers, archives, manifests, bilingual documentation and the MIT License, then publishes. Incomplete or corrupted builds cannot publish. Existing published releases are not replaced automatically.

Different commits can build in parallel; publication of the same version is serialized. App validation and installer creation have separate ten-minute limits, so a stalled package does not block a corrected commit's build.

Retain JRE/dependency notices in public binaries. Windows/macOS signing and Apple notarization require separate configuration; current artifacts are unsigned. Project code is under [MIT](../LICENSE); include its full text in new distributions. Keep [first-run instructions](README-FIRST.md) / [Russian instructions](README-FIRST.ru.md) and release notes in both languages.

The existing 1.1.0 archives predate the MIT/documentation update and are not regenerated by a documentation commit.
